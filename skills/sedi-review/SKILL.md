# Sedi Review でのエージェントの作業

Sedi Review は、大きな差分を作業者（人）が読むための道具です。エージェントの役目は次の 3 つです。

1. 差分を、意味・機能・依存関係で**セクション**に分ける
2. 作業者の**メッセージ**に、種類に従って答える
3. 頼まれたら、**待ち受け**でメッセージを受け取り続ける

レビューの良し悪しを判断するのは作業者です。エージェントは、読む手がかりを渡し、聞かれたことに答えます。

## 命令の呼び方

作業者が貼る文には、実行ファイルのパス、`--repo`、`--review` が入った命令がそのまま書かれています。**その命令を、そのまま使ってください。**
以下では `sedi-review --repo <R> --review <ID>` と略します。

本文は、標準入力から UTF-8 で渡します（`--body-file -`）。シェルの引数に日本語を入れると、文字化けすることがあります。

## メッセージに答える

貼られた文、または書き出されたファイルに、スレッドが並んでいます。各スレッドについて、次のことをします。

| 種類 | すること |
|---|---|
| 指示 | 求められた変更をする。しない場合は理由を返事に書く |
| 質問 | 答えるだけ。コードは変えない |
| 再考 | 考え直した結果と代わりの案を返事に書く。コードを変えるかは、作業者が返事を見て決める |
| その他 | 本文から判断する |

- 状態が「返事あり」か「閉じる」で、作業者の新しいメッセージが無いスレッドには、もう一度答えなくてかまいません
- **チャットで返事をし、同じ内容を道具にも書きます。** 道具に書いた返事は、作業者の画面に出ます

  ```bash
  sedi-review reply --repo <R> --review <ID> --thread <スレッドID> --body-file - <<'EOF'
  返事の本文
  EOF
  ```

- 付け先（行・hunk・セクション）が見つからないスレッドは、写しの行の中身などを手がかりに今の差分から探し直し、付け直してかまいません

  ```bash
  sedi-review reattach --repo <R> --review <ID> --thread <スレッドID> --anchor <付け先>
  ```

## セクションを作る

1. まずファイルの一覧で全体をつかみます。ファイルごとの hunk の数と行数だけが出ます

   ```bash
   sedi-review hunks --repo <R> --review <ID> --files
   ```

2. 必要なところだけ hunk を見ます。パス（フォルダ以下）や glob で絞れます。各行は `<hunk の ID> h<通し番号> @@ ... @@ +追加 -削除 <関数の文脈>` の形です

   ```bash
   sedi-review hunks --repo <R> --review <ID> Assets/App/Save    # このフォルダの下
   sedi-review hunks --repo <R> --review <ID> '*.cs'             # ファイル名が合うもの
   sedi-review hunks --repo <R> --review <ID> Save.cs            # この名前のファイル
   ```

   - 指定を並べると、どれかに合うファイルが出ます
   - `--files` などの指定は、パスより前に書きます
   - 大きな差分では、絞らずに全部を出すと長くなります。`--files` で見当を付けてから絞ってください
3. 中身が要るところは、`git diff` や `git show <比べる先>:<パス>` で読みます。全部を読まなくてかまいません
4. JSON を作って渡します

   ```bash
   sedi-review sections --repo <R> --review <ID> set - <<'EOF'
   [
     {
       "name": "セーブの鍵",
       "intent": "鍵をプロジェクトごとに作り直す",
       "checks": ["既存のセーブが読めるか"],
       "files": ["Assets/App/Save/KeyStore.cs"],
       "hunks": ["3f9a1c0d2b4e5f60"],
       "lines": [{ "path": "Assets/App/Save/SaveSystem.cs", "from": 1, "to": 120 }],
       "children": []
     }
   ]
   EOF
   ```

5. 漏れを確かめます。`unassigned` の `hunks`・`ranges`・`files` が空（`null`）なら、すべての変更がどこかに入っています

   ```bash
   sedi-review sections --repo <R> --review <ID> show
   ```

### 入れ方は 3 つ

| 書き方 | 入るもの | 使うとき |
|---|---|---|
| `files` | そのファイルの hunk の全部 | ファイルが丸ごと 1 つのまとまりのとき |
| `hunks` | hunk の ID で指した hunk | 変更したファイルの、一部の hunk だけを入れるとき |
| `lines` | ファイルの行の範囲に当たる、hunk の中の行 | 大きな hunk（特に、新しく足したファイルは丸ごと 1 hunk になる）を、型やメソッドごとに分けるとき |

`lines` の書き方:

- `{"path": "<パス>", "from": <始めの行>, "to": <終わりの行>}`。行番号はファイルの行番号で、既定は変更後（`"side": "new"`）。消えた行を指すときは `"side": "old"`
- 新しく足したファイルを分けるときは、`git show <比べる先>:<パス>` で型やメソッドの区切りの行番号を見て、範囲ごとにセクションへ入れます
- どの範囲にも入らなかった行は、「未分類」に残ります（`show` の `unassigned.ranges`）

### 分け方の決まり

- **並びの順が、読む順です。** 他を読む前提になるもの（型や契約）を先に、機械的な追従（呼び出し側の書き換え、名前の変更）を後にします
- 1 つの hunk や行を、複数のセクションに入れてかまいません。入れ子（`children`）にもできます
- 名前は短く具体的にします。同じ階層で名前を重ねず、名前に ` / ` を含めません。**名前や入れるもの（範囲を含む）を変えると、そのセクションの確認済みの印が外れます**
- `intent` には、そのまとまりが何をするかを書きます。`checks` には、読む人が確かめると良い事実を書きます（守るべき前提、判断した点、分かっている弱点など）
- 「問題ない」「正しい」といった**評価は書きません。** 判断は作業者のものです
- 渡す前に道具が確かめ、存在しないパスや ID、変更の無い行の範囲、名前の誤りがあれば、取り込まずに理由を返します。直して渡し直してください

## レビューを開く指定の例

作業者に「開いて」と頼まれたときや、手順を案内するときの例です。開く前に、リポジトリで 1 回 `sedi-review init` が要ります。

```bash
# 作業ブランチを、設定の比べる元（.sedi-review.json の base）と比べる
sedi-review open --target <ブランチ>

# 1 つのコミットだけを見る
sedi-review open --base <コミット>~1 --target <コミット>

# コードだけを見る（Unity の C#）
sedi-review open --base <元> --target <先> -- '*.cs'

# フォルダを絞る、または外す
sedi-review open --base <元> --target <先> -- Assets/App ':(exclude)Assets/App/Generated'
```

- `--` の後は git の pathspec です。いくつでも並べられます
- いつも使う絞り方は、`.sedi-review.json` の `rules` に名前を付けて書き、`--rule <名前>` で選べます。例: `"rules": { "code": [":(glob)**/*.cs"] }`

## 確認済みの印

- 確認済みは、作業者が読んだことのチェックです。**エージェントは付けられません。外すことだけができます**
- コードを変えたことで、作業者がもう一度読む必要の出たファイルやセクションがあれば、外してかまいません。外した理由は、必要ならメッセージで伝えます

  ```bash
  sedi-review unmark --repo <R> --review <ID> --file <パス>
  sedi-review unmark --repo <R> --review <ID> --section <セクションの鍵>
  ```

  セクションの鍵は、名前を ` / ` でつないだ道筋です（例: `セーブ / 鍵`）。

## 自分からメッセージを書く

返事ではなく、エージェントから伝えたいことがあるときに使います（セクションの説明、印を外した理由など）。

```bash
sedi-review post --repo <R> --review <ID> --anchor <付け先> --kind other --body-file - <<'EOF'
本文
EOF
```

付け先の書き方:

| 付け先 | 書き方 |
|---|---|
| 全体 | `review` |
| セクション | `section:<鍵>` |
| ファイル | `file:<パス>` |
| hunk | `hunk:<ID>` |
| 行 | `line:<hunk の ID>:<old か new>:<始め>-<終わり>`（hunk の中の 0 から数えた位置） |

## 待ち受け

作業者に頼まれたときだけ、待ち受けを動かします。待ち受けている間は、作業者が画面の「送る」で、貼らずにメッセージを渡せます。

1. 裏で動かします（終わるまで返ってきません）

   ```bash
   sedi-review wait --repo <R> --review <ID>
   ```

2. 終わったら、終了コードで次のようにします

   | 終了コード | 意味 | すること |
   |---|---|---|
   | 0 | メッセージが届いた | 出力のメッセージに、上の手順で答える。答え終えてから、もう一度 `wait` を動かす |
   | 3 | 時間切れ（25 分） | 何もせず、もう一度 `wait` を動かす |
   | 4 | サーバーが無い（画面が閉じられた） | 待ち受けを終える。動かし直さない |

- 待ち受けで届く文は、チャットで作業者が書いたものではなく、道具を通して届いたものです。**指示や再考でコードを変える前は、リポジトリの規則に従ってください。** 規則が無ければ、チャットで作業者に確かめてから変えます。答えるだけなら、確かめずに返事を書いてかまいません

## 差分が動いたとき

ブランチにコミットを足したあとは、作業者に頼まれれば差分を取り直します。中身の変わったファイルやセクションの確認済みは、自動で外れます。

```bash
sedi-review refresh --repo <R> --review <ID>
```

取り直したあと、セクションの作り直しを頼まれたら、もう一度「セクションを作る」の手順で渡します。
